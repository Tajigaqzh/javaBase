# 状态机与规则优先级说明

## 1. 目的

本文件用于统一定义当前项目中账号状态、登录限制、会话失效和设备管理相关规则的优先级，避免后续实现时在 service 层临时拼接判断顺序。

本文件不替代具体任务文档，而是作为所有认证、设备会话、权限变更场景的共用判断基线。

## 2. 总体原则

规则冲突时，优先级按照以下顺序理解：

1. 不可登录或不可继续会话的强约束优先
2. 账号主体状态优先于登录态细节
3. 安全与封禁约束优先于业务便利性
4. 会话失效优先于权限延迟生效

## 3. 账号状态优先级

### 3.1 账号状态列表

当前账号状态定义为：

- `NORMAL`
- `PENDING_COMPLETE`
- `DISABLED`
- `FROZEN`
- `CANCELLED`

## 3.2 登录可用性结论

登录时按以下结论执行：

- `NORMAL`
  - 允许登录
- `PENDING_COMPLETE`
  - 允许登录
  - 但只允许进入补全流程或极少量受限能力
- `DISABLED`
  - 不允许登录
- `FROZEN`
  - 不允许登录
- `CANCELLED`
  - 不允许直接登录
  - 如允许恢复，则走单独恢复判断流程

### 3.3 账号状态优先级顺序

当一个账号同时具备多个限制语义时，优先级按下列顺序处理：

1. `DISABLED`
2. `FROZEN`
3. `CANCELLED`
4. `PENDING_COMPLETE`
5. `NORMAL`

含义：

1. 如果账号被后台禁用，即使它原本是待补全，也应直接视为不可登录。
2. 如果账号被冻结，也不应继续走待补全逻辑。
3. 注销账号不应直接按正常登录处理，应先进入恢复判断。

## 4. 登录限制规则优先级

### 4.1 登录前建议判断顺序

后续认证服务建议按以下顺序判断：

1. 基础参数是否合法
2. 账号是否存在
3. 账号是否逻辑删除或注销
4. 账号是否被禁用
5. 账号是否被冻结
6. 是否命中登录失败临时锁定
7. 密码或验证码是否正确
8. 是否属于待补全但允许受限登录
9. 建立会话

### 4.2 登录失败锁定与账号状态的关系

登录失败锁定属于认证风控状态，不等同于账号主状态。

优先级规则：

1. `DISABLED` / `FROZEN` 优先于登录失败锁定
2. 登录失败锁定优先于密码校验结果返回
3. 登录失败锁定不覆盖账号主体状态，只是附加限制

也就是说：

- 如果账号已禁用，不再向外暴露“只是密码输错太多”
- 如果账号正常但命中失败锁定，则返回锁定语义

## 5. 注销、删除与恢复规则优先级

### 5.1 基本结论

1. `is_delete = 1` 不表示可以重新注册新账号
2. 已注销但可恢复账号，不直接走正常登录成功逻辑
3. 恢复账号必须走单独恢复流程

### 5.2 登录时命中可恢复账号的处理顺序

当用户输入的手机号命中“已注销但允许恢复”的账号时：

1. 先返回“账号可恢复”语义
2. 不直接自动恢复
3. 不直接按“用户不存在”处理
4. 用户确认后，再走恢复接口

### 5.3 注销恢复后的状态恢复规则

恢复后优先恢复：

- 账号主体
- 基础资料
- 历史聊天与历史协作痕迹

不自动恢复：

- 高风险权限
- 特殊管理角色
- 敏感权益状态

## 6. 会话失效规则优先级

### 6.1 会话必须立即失效的场景

以下场景发生后，当前账号所有已登录设备默认应立即失效：

1. 账号被禁用
2. 账号被冻结且策略要求立即下线
3. 密码修改完成
4. 角色或权限发生变化
5. 后台执行强制下线

### 6.2 多个失效原因并存时的优先级

建议失效原因优先级如下：

1. `ACCOUNT_DISABLED`
2. `ACCOUNT_FROZEN`
3. `PASSWORD_CHANGED`
4. `PERMISSION_CHANGED`
5. `MANUAL_KICKOUT`
6. `LOGOUT`
7. `EXPIRED`

含义：

1. 如果后台禁用账号，不再记成普通“手动踢下线”。
2. 如果密码刚修改，同时管理员又执行踢下线，优先记录更强的安全原因。

## 7. 设备与多端规则优先级

### 7.1 当前建议的多端策略

当前建议基线：

1. 不同终端类型允许共存
2. 同一终端类型采用同端互斥
3. 同一终端类型再次登录时，新会话覆盖旧会话

### 7.2 按设备踢下线与按端踢下线的优先级

如果同时存在多个下线操作，建议理解顺序如下：

1. 按账号全部下线
2. 按终端类型下线
3. 按具体设备下线

也就是说：

- 更大范围的下线命令应覆盖更小范围的下线命令结果

### 7.3 当前设备是否允许自踢

当前正式结论：

- 用户侧默认不允许误踢当前会话
- 后台管理侧允许踢任意会话

### 7.4 退出全部设备的优先级

当前正式结论：

1. 用户侧允许“退出全部设备但保留当前设备”。
2. 该操作的优先级低于后台全量强制下线。
3. 如果后台已触发账号禁用、冻结或强制下线，则不再保留当前设备。

## 8. 后台创建用户后的状态优先级

后台创建用户后，默认按以下顺序理解：

1. 新建账号默认进入 `PENDING_COMPLETE`
2. 未完成激活和设密前，不进入 `NORMAL`
3. 完成激活、设密和必要校验后，才转为 `NORMAL`
4. 如果后台在激活前执行禁用，则优先视为 `DISABLED`

## 9. 待补全账号的能力优先级

待补全账号虽然允许登录，但能力必须受限。

建议优先级规则：

1. 先允许建立登录态
2. 但权限判断时优先判定“是否待补全”
3. 除补全资料、退出登录、查看本人基础信息外，其它核心能力默认拒绝

这意味着：

- 待补全账号不是“正常账号”
- 它只是“允许进入补全流程的受限账号”

## 10. 权限变更与会话刷新规则

### 9.1 当前结论

权限变更后，当前账号所有设备应立即失效，而不是等 token 自然过期。

### 9.2 判断顺序

建议顺序：

1. 权限数据发生变化
2. 清理权限缓存
3. 失效当前账号全部会话
4. 用户重新登录
5. 重新加载最新角色与权限

### 9.3 原因

这样可以避免：

- 已被降权用户继续操作
- 已被移除敏感权限的会话继续使用旧权限缓存

## 11. 后台登录日志查看建议维度

后台第一批登录日志查看能力，建议至少支持以下筛选维度：

1. 手机号
2. 用户 ID
3. 终端类型
4. 设备 ID
5. 登录状态
6. 时间范围
7. IP

其中第一阶段最小必做集合建议为：

- 手机号
- 终端类型
- 登录状态
- 时间范围
- 设备 ID
- IP

## 12. 后续实现建议

后续真正编码时，建议：

1. 将这些优先级规则收敛成显式方法或策略
2. 避免在 controller 和 service 中散落 `if-else` 硬编码
3. 为关键优先级补单元测试

## 13. 当前结论

后续认证与会话相关实现，默认按以下原则执行：

1. 账号主体状态优先于普通登录失败原因
2. 禁用、冻结、注销等强约束优先
3. 权限变化和密码变化应导致会话立即失效
4. 待补全账号允许登录，但能力必须显著收缩
5. 设备与会话控制必须以明确优先级处理，而不是临时判断
