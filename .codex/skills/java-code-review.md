# Java 代码评审

## 概述

当你在 Spring Boot 或 Maven Java 项目中进行代码评审，且重点是发现缺陷、行为回归、设计风险和测试缺口时，使用这份指南。

## 评审重点

1. 正确性

- 检查空值处理、边界条件、异常路径、事务边界以及接口契约是否发生不合理变化。
- 确认 controller、service、mapper、DTO、entity 的职责划分与项目结构保持一致。

2. 数据与持久化

- 检查是否存在高风险 SQL、N+1 查询、缺少分页、过滤条件薄弱、Mapper 与 XML 不一致等问题。
- 确认实体字段变更是否与表结构、查询映射保持一致。

3. Spring 行为

- 检查依赖注入方式、Bean 生命周期假设、配置绑定、请求校验是否合理。
- 关注是否缺少 `@Transactional`、`@Valid`，或存在错误的 Web 映射。

4. 测试

- 确认新增逻辑和变更分支已有测试覆盖。
- 对缺失的异常场景、边界场景、集成路径测试进行明确指出。

5. 表结构与字段规范

- 检查表名、字段名是否语义清晰，避免拼音缩写、含义模糊或与业务不一致的命名。
- 优先使用小写字母加下划线风格的表名和字段名，名称应可直接表达业务含义。
- 检查主键、唯一索引、普通索引设计是否与查询场景匹配，避免缺索引或无效索引。
- 检查字段类型是否合理，避免 `varchar` 长度随意放大、金额使用浮点、状态值语义不清。
- 检查是否包含必要的通用字段，如创建时间、更新时间、创建人、更新人、逻辑删除标记，并确认语义一致。
- 检查是否避免使用数据库保留字、过度允许 `null`、以及默认值设计混乱的问题。
- 检查布尔或状态字段是否具备清晰取值定义，避免 `status1`、`type2` 这类不可维护命名。

6. 代码规范

- 以 `.codex/skills/java-code-style.md` 为代码编写基准，重点检查改动是否偏离仓库既定写法。
- 对命名、方法长度、分支复杂度、重复代码、异常处理、日志输出、注释质量中的明显偏差给出问题结论。
- 对单个方法超过 80 行、核心类缺少头部职责说明、关键方法缺少顶部注释的情况，视为明确可指出的问题。
- 对测试类缺少类头注释、测试范围说明不清、复杂测试场景缺少必要说明的情况，也应作为质量问题指出。

7. 工程规范

- 检查分层是否清晰，controller 不承载业务规则，service 不做无意义透传，mapper 不混入业务判断。
- 检查接口入参与出参是否使用 DTO/VO，而不是直接暴露数据库实体承载复杂协议。
- 检查公共能力是否沉淀到合适模块，避免横向复制工具类、常量类、转换逻辑。
- 检查配置项是否可维护，敏感配置不得硬编码在代码或仓库中。
- 检查依赖引入是否必要，避免为了少量功能引入重量级依赖，或引入重复能力依赖。
- 检查变更是否破坏模块边界、增加循环依赖、或让低层模块反向依赖高层业务模块。

## 阿里规约对齐检查

### 编程规约

- 命名不得以下划线或美元符号开头或结尾，避免中英文混用、拼音缩写和含义不明缩写。
- 类名使用 `UpperCamelCase`，方法、参数、成员变量、局部变量使用 `lowerCamelCase`，常量使用全大写下划线分隔。
- 抽象类优先使用 `Abstract` 或 `Base` 前缀；异常类以 `Exception` 结尾；测试类应与被测类语义对应。
- 强制关注魔法值、过长方法、过深嵌套、复杂布尔表达式、重复代码和可读性差的控制流。
- 所有覆写方法应显式使用 `@Override`；禁止通过对象引用访问静态成员。
- 包装类比较优先使用 `equals`；浮点计算避免直接用 `==`；金额与精确数值优先使用 `BigDecimal`。
- DO/DTO/VO 等 POJO 属性不要设置业务默认值；布尔属性命名避免直接以 `is` 作为 Java 字段前缀。

### 异常与日志

- 异常不能作为流程控制手段；`catch` 之后必须处理、转换或继续抛出，禁止吞异常。
- 事务代码中捕获异常时，必须显式关注回滚语义，避免吞异常导致事务未正确回滚。
- `finally` 中必须释放资源，且不要在 `finally` 中写 `return`。
- 日志统一通过 `SLF4J` 门面输出，避免直接耦合具体日志实现。
- 日志内容必须包含案发现场和异常堆栈；禁止无意义重复打印、敏感信息泄露和高频字符串拼接日志。
- `debug`/`trace` 日志应配合级别判断，避免无意义的字符串构造和方法调用开销。

### 单元测试

- 单元测试应满足自动化、独立性、可重复执行，不依赖执行顺序、外部环境和人工观察输出。
- 测试代码必须放在 `src/test/java`，断言必须使用测试框架断言，而不是 `System.out`。
- 核心业务、核心模块、增量代码必须补测试；评审时重点检查是否符合 `BCDE` 原则：
- `B`：边界值，如空值、长度、顺序、分页、临界条件。
- `C`：正确输入与预期输出。
- `D`：是否覆盖设计上的关键分支和规则。
- `E`：错误输入、异常流程、非法场景。

### 安全规约

- 对外接口、用户输入、分页参数、排序字段、重定向地址等必须校验，避免注入、越权、内存打爆和 ReDoS 风险。
- 用户敏感数据展示必须脱敏；用户专属资源必须做权限控制，避免水平越权。
- SQL 必须参数化，禁止字符串拼接；页面输出必须转义，避免 XSS。
- 涉及短信、邮件、下单、支付、验证码等资源型接口时，必须检查防重放、防刷和频控能力。

### MySQL 规约

- 布尔语义数据库字段优先使用 `is_xxx`，Java POJO 字段不要直接用 `isXxx` 命名。
- 表名、字段名必须小写加下划线，避免复数表名、保留字、不清晰缩写和无注释状态字段。
- 主键索引命名为 `pk_字段名`，唯一索引为 `uk_字段名`，普通索引为 `idx_字段名`。
- 金额字段禁止使用 `float`/`double`；超长文本和大字段应与主表解耦，避免影响索引效率。
- SQL 查询禁止 `select *`；分页、索引、`count(*)`、`sum()` 的空值处理、`IN` 数量和隐式类型转换都应重点检查。
- 禁止依赖外键级联、存储过程和无审慎校验的数据订正语句。

### 工程结构与设计

- 分层上遵循 controller、service、manager、dao 各司其职，避免层间职责漂移。
- 查询参数超过两个时，优先封装查询对象，避免 `Map` 到处传递。
- 二方库依赖需关注版本统一、避免 `SNAPSHOT` 上线、避免同坐标多版本冲突。
- 设计评审时要关注状态流转、调用链复杂度、数据结构演进和异常流程，而不仅是主流程“能跑通”。

## 提交前门禁

- 将提交前校验视为功能变更的强制要求，尤其是新增或修改 HTTP 接口时。
- 当新增 controller 接口、请求路径或对外可见的 service 行为时，必须检查是否存在覆盖该接口的对应测试文件或测试用例。
- 如果新增接口但没有匹配测试，应作为评审问题提出，不能当作可选建议略过。
- `.githooks/` 只提供基础门禁，评审时仍需人工确认测试场景是否充分，而不是仅以 Hook 通过作为结论。

## 新增接口测试要求

- 每个新增接口都要验证是否存在成功路径测试。
- 验证是否覆盖边界测试，包括非法参数、空值、null、枚举或业务取值边界、分页边界及其他适用于该接口的输入边界。
- 验证是否覆盖必要的失败路径测试，包括参数校验失败、业务异常、依赖失败，以及存在安全控制时的未授权或无权限场景。
- 验证返回断言不仅检查“接口能返回”，还应覆盖状态码和关键业务字段。
- 如果接口会触发持久化变更，应确认相关 service 测试或集成测试覆盖写入结果与查询一致性。

## 提交前测试执行要求

- 在 commit 之前，必须执行覆盖本次新增或修改功能的相关测试，不能只做泛化的抽样检查。
- 优先执行受影响的目标测试类；当变更涉及共享基础设施或横切逻辑时，还应补充执行更大范围的必要测试集。
- 如果变更新增了接口，但没有可执行的对应测试，应将其视为工作未完成，并明确指出。
- 需要记录是否执行了测试、执行了哪些范围，以及当前仍缺失哪些必要覆盖。
- 在 commit 之前，还必须检查注释规范是否满足要求，包括类头部职责注释、关键核心方法顶部注释，以及注释与实现是否一致。

## 不符合规范时的报告要求

- 如果改动不满足当前 review skill 或 `java-code-style` 的要求，应在 `.codex/` 目录下生成检查报告或重构建议，而不是只在对话里口头带过。
- 建议统一输出到 `.codex/reports/code-quality-review.md`。
- 报告至少应包含：
- 问题文件与方法位置
- 问题类型
- 风险说明
- 建议的修复方式或重构方向
- 是否阻塞 commit

## 输出要求

- 先给出问题，按严重程度排序。
- 每条问题都要包含明确的文件位置和简洁的原因说明。
- 总结保持简短，重点放在可执行的评审意见上。

## 评审偏好

- 参考头部互联网公司常见规范时，优先吸收那些能直接降低线上风险、提升可维护性的规则，而不是机械照搬全部条文。
- 若规范与当前项目既有约定冲突，优先指出冲突点与风险，再结合仓库现状给出可执行建议。
- 对数据库设计、命名、异常处理、日志、分层、测试覆盖等基础质量项，默认按高标准审查。
- 参考《Java 开发手册》时，优先按照“强制 > 推荐 > 参考”的优先级执行；评审结论中应优先暴露强制类问题。

## 不适用场景

- 如果任务是从零实现功能，而不是评审现有改动，则不应把这份指南当作主流程。
- 如果只是纯样式或格式层面的反馈，且不存在行为、正确性、维护性风险，则不应过度套用本指南。
