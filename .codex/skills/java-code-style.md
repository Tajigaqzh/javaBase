# Java 代码编写规范

## 使用场景

当任务重点是编写、修改、重构 Java 代码，而不是单纯做代码评审时，优先遵循本规范。

适用范围：
- Spring Boot 接口开发
- Service 业务逻辑实现
- MyBatis-Plus / MyBatis 数据访问代码
- DTO、VO、Entity、Mapper、测试代码编写
- 日常重构、修 Bug、补测试、补校验

## 总体原则

- 优先写清晰、稳定、易维护的代码，不为了“炫技巧”牺牲可读性。
- 优先遵守项目现有分层和约定，不随意创造新风格。
- 先保证正确性，再考虑抽象；先保证简单可读，再考虑复用。
- 新增代码默认要考虑边界、异常、日志、测试，而不是只写主流程。

## 命名规范

- 类名使用 `UpperCamelCase`。
- 方法名、参数名、成员变量、局部变量使用 `lowerCamelCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 包名全部小写，使用单数语义英文单词，避免拼音、中文、随意缩写。
- 抽象类优先使用 `Abstract` 或 `Base` 前缀。
- 异常类以 `Exception` 结尾。
- Service/DAO 接口与实现类分离，实现类使用 `Impl` 后缀。
- 测试类优先使用被测类名加 `Tests`，与当前仓库约定保持一致。

禁止事项：
- 禁止以下划线或美元符号作为命名开头或结尾。
- 禁止中英文混用、拼音缩写、语义不清缩写。
- 禁止使用 `data`、`temp`、`obj`、`xxx` 这类低信息量命名，除非作用域极小且语义明确。

## 分层规范

### Controller 层

- 只负责接收请求、基础参数校验、调用 service、返回统一响应。
- 不直接写 SQL。
- 不承载复杂业务规则。
- 不直接操作多个 mapper 拼业务流程。
- 接口入参优先使用 DTO，出参优先使用 VO。
- 接口涉及参数校验时，优先结合 `@Valid`、`@Validated` 和显式业务校验。

### Service 层

- 承载明确的业务语义、流程编排和事务边界。
- 不要写成纯透传层；如果只是单行转调，需要评估是否冗余。
- 跨多个 DAO/Mapper 的业务组合应放在 service。
- 事务逻辑、状态流转、幂等控制、业务校验优先放在 service。

### Mapper / DAO 层

- 只负责数据访问。
- 不写业务判断、流程控制、状态机逻辑。
- 简单 CRUD 优先走规范写法，复杂查询写到 XML 并保证 SQL 可读性。
- 返回类型、参数类型、实体映射必须稳定清晰。

## 方法编写规范

- 单个方法必须尽量保持短小，默认不超过 80 行；超过时应优先拆分，并说明无法继续拆分的原因。
- 一个方法只做一类核心事情，避免同时做校验、查询、转换、写库、组装返回、打日志等过多职责。
- 优先使用卫语句减少多层嵌套。
- `if/else` 嵌套超过 3 层时，应考虑拆方法、策略模式、状态模式或提前返回。
- 复杂布尔表达式先拆成具名布尔变量，再进入条件判断。
- 不要在条件表达式中夹带赋值。

优先写法：
- 先处理非法输入、空数据、异常状态，再进入主干逻辑。
- 把通用校验、通用转换、通用查询抽到私有方法或公共组件。

避免写法：
- 超长方法
- 巨型 `if-else`
- 一个方法里做所有事情
- 方法名和行为不一致

## 对象与模型规范

- Entity / DO 与数据库表结构保持一致。
- DTO 用于接口入参或服务传输，不直接承担数据库实体职责。
- VO 用于接口返回展示，不把数据库内部字段直接原样暴露出去。
- 不要把复杂接口直接用 Entity 作为入参。
- POJO 类属性不要随意设置默认值，避免更新或映射时引发脏数据。
- POJO 的布尔属性避免直接使用 `isXxx` 作为 Java 字段名。

## 常量与枚举

- 禁止魔法值直接散落在代码中。
- 常量按功能归类，不要堆在一个巨大常量类里。
- 有限状态、固定范围取值优先使用 `enum`，不要用裸字符串或裸数字硬编码。
- 枚举应表达清晰业务语义，必要时带业务码值和说明。

## 空值与边界处理

- 所有外部输入默认不可信，必须考虑 `null`、空串、空集合、非法值、越界值。
- 调用链过长时注意空指针风险，避免无保护链式调用。
- 返回集合时，遵循项目既有约定；若返回 `null`，必须有充分语义和上层处理保障。
- 使用包装类型时注意自动拆箱风险。

## 异常处理规范

- 异常不能当正常流程控制使用。
- `catch` 之后必须处理、转换或继续抛出，禁止吞异常。
- 业务异常和系统异常应尽量分层表达，不要只抛 `RuntimeException`。
- 事务方法中捕获异常后，必须明确考虑回滚语义。
- `finally` 中负责资源清理，不要写 `return`。
- 最外层返回给前端或调用方的错误信息应可理解，不能直接暴露底层异常细节。

## 日志规范

- 统一使用 `SLF4J`。
- 使用占位符，不做无意义字符串拼接。
- 日志要包含关键业务上下文，能帮助定位问题。
- 禁止打印密码、Token、密钥、身份证号、手机号明文等敏感信息。
- 高频路径避免滥打 `info` 和 `warn`。
- 调试级日志在复杂参数计算前先判断级别。

## 集合与流式处理规范

- 集合定义使用泛型。
- 初始化大集合时指定合理初始容量。
- 遍历 `Map` 优先使用 `entrySet`。
- 不要在 `foreach` 中直接做集合删除。
- 使用 `subList`、`Arrays.asList`、不可变集合时注意修改限制和视图副作用。
- 使用 Stream 时以提升可读性为前提，不要为了函数式而函数式。

## 并发与线程规范

- 线程资源优先通过线程池管理，不直接手写大量线程创建。
- 线程池优先显式配置 `ThreadPoolExecutor` 语义，不盲目用 `Executors` 默认工厂。
- 锁要尽量小粒度，避免持锁执行 RPC、数据库慢操作或复杂循环。
- 使用 `ThreadLocal` 后必须清理，尤其在线程池场景。
- 时间格式化优先使用 JDK 8 时间 API，避免共享 `SimpleDateFormat`。

## 数据库与 SQL 编写规范

- 表名、字段名优先小写下划线风格，语义清晰。
- 布尔语义字段优先使用 `is_xxx`。
- 金额类型使用 `BigDecimal` / `decimal`，禁止浮点表示金额。
- 查询禁止无脑 `select *`，明确列出需要字段。
- 新增查询要考虑索引命中、分页、排序和返回字段大小。
- 复杂 SQL 写 XML，并注意可读性。
- 避免 N+1 查询、无条件全表扫描、左模糊导致索引失效。
- 分页查询应先关注总数判断、边界页处理和大偏移性能风险。

## 安全规范

- 用户输入必须校验。
- SQL 参数必须参数化，禁止字符串拼接 SQL。
- 用户私有数据、后台管理操作、资源型接口必须考虑鉴权、防刷、限流、幂等和脱敏。
- 返回给前端的字段要有最小暴露原则，不要把内部标识、敏感字段、调试字段直接透出。

## 注释规范

- 每个新增或显著修改的 `.java` 文件，在类定义上方应提供清晰注释，说明当前类、工具类、枚举或配置类的核心作用。
- 类头部注释应尽量覆盖以下信息：
- 这个类是做什么的。
- 提供了什么核心功能或承担什么职责。
- 依赖了哪些关键组件、服务、Mapper、配置或外部能力。
- 如果是工具类、枚举、配置类、切面、异常类，也要说明其使用场景或作用边界。
- 公共类、核心业务类、复杂流程类优先使用 Javadoc 风格注释，而不是零散单行备注。
- 类、接口、公共方法在必要时写 Javadoc，重点说明用途、参数、返回值、约束和异常语义。
- 注释应解释“为什么”，不要翻译代码本身。
- 修改代码时同步修改注释，避免注释失真。
- 过期注释、误导注释、注释掉的大段废弃代码应清理。

## 核心方法注释规范

- 对关键核心方法，必须在方法顶部增加较详细注释，帮助阅读者快速理解该方法的业务意图和执行路径。
- 以下方法默认视为需要重点注释的方法：
- 复杂业务编排方法
- 事务入口方法
- 状态流转方法
- 核心校验方法
- 涉及缓存、鉴权、限流、幂等、重试、补偿的关键方法
- SQL 或数据写入影响较大的关键方法
- 核心方法注释应尽量说明：
- 该方法解决什么问题。
- 主要执行步骤或处理流程。
- 关键入参约束或前置条件。
- 依赖哪些服务、Mapper、缓存、配置或外部系统。
- 可能抛出的关键异常、失败路径或边界场景。
- 对于简单 getter、setter、极短的纯工具方法，不要求强行补充大段注释。

## 测试编写规范

- 新增功能默认补测试，不只写主流程。
- 新增接口至少覆盖成功路径、参数校验失败、边界值、业务异常，以及必要的持久化或集成路径。
- 测试应自动化、独立、可重复执行。
- 使用断言验证结果，不使用 `System.out` 做人工判断。
- 测试数据准备要可控，避免强依赖外部环境和脏数据。

## 提交前自检清单

- 是否遵守分层职责，没有把业务塞进 controller 或 mapper。
- 是否补齐了新增接口和新增分支的测试。
- 是否覆盖了边界、异常、空值、非法输入。
- 是否存在魔法值、重复代码、超长方法、深层嵌套。
- 是否存在敏感日志、异常吞掉、事务边界不清。
- 是否评估了 SQL、索引、分页和返回字段。
- 是否检查了类头部注释、核心方法顶部注释、注释与代码是否同步更新。
- 是否执行了 `./mvnw clean compile`、`./mvnw test` 以及本次功能相关测试。

## 不符合规范时的输出要求

- 如果当前代码改动不满足本规范，不应直接忽略问题。
- 应在 `.codex/` 目录下输出一份检查报告或重构建议，便于后续继续处理。
- 建议使用统一路径：
- `.codex/reports/code-quality-review.md`
- 报告内容应尽量包含：
- 不符合规范的文件和方法
- 违反了哪些规则
- 问题的影响
- 可执行的重构建议或修复建议
- 如果问题暂时不修复，也应在报告中说明原因和风险。

## 与代码评审 Skill 的关系

- 本规范用于“写代码、改代码、重构代码”。
- `.codex/skills/java-code-review.md` 用于“审代码、查风险、查测试缺口”。
- 实际开发中，可先按本规范实现，再按 review skill 做提交前复查。
